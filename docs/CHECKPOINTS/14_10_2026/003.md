## 11. CONTRATO MÍNIMO DEL ADAPTADOR SUPER CMS — AUTORIZADO

Fecha: 14/10/2026
Estado: DISEÑO DOCUMENTAL — SIN IMPLEMENTACIÓN

### 11.1 Objetivo

Definir un contrato verificable entre los datos JSON de una página y una plantilla HTML elegida explícitamente, sin alterar los editores, las plantillas originales ni la API existente.

### 11.2 Entradas del adaptador

- Identificador del proyecto.
- Slug válido de la página.
- Título de la página.
- Bloques de contenido con tipo y datos.
- Identificador técnico explícito de la plantilla.
- Configuración y requisitos declarados de dicha plantilla.

La entrada debe validarse antes de procesarse. No se deben inferir identificadores ni seleccionar una plantilla por defecto.

### 11.3 Flujo contractual

1. Recibir los datos JSON.
2. Validar estructura, tipos y campos obligatorios.
3. Resolver la plantilla mediante un identificador explícito.
4. Comprobar que la plantilla existe y está habilitada.
5. Validar la compatibilidad entre bloques, datos y plantilla.
6. Procesar únicamente la sintaxis declarada para esa plantilla.
7. Verificar el HTML resultante y detectar marcadores sin resolver.
8. Devolver HTML y un resultado de validación comprensible.
9. Mantener intactos los archivos originales.

### 11.4 Seguridad y fallos

- Rechazar identificadores de proyecto, slug o rutas no válidos.
- Escapar correctamente los valores insertados en texto y atributos HTML.
- No interpretar datos de usuario como código ejecutable.
- No continuar si faltan campos obligatorios o la plantilla no está autorizada.
- No sustituir silenciosamente una plantilla incompatible por otra.
- No declarar éxito si quedan marcadores sin resolver o falla la validación.
- No sobrescribir plantillas, demos ni el editor HTML original.

### 11.5 Compatibilidad inicial

La primera prueba utilizará una plantilla con marcadores simples explícitamente identificados.

Las plantillas que utilicen valores predeterminados, rutas anidadas o bloques repetibles quedan pendientes de un perfil de sintaxis propio y de pruebas específicas.

### 11.6 Prueba aislada prevista

La prueba deberá utilizar datos ficticios y producir un archivo HTML temporal fuera de las plantillas oficiales.

Casos mínimos:
- Entrada válida: generar HTML y comprobar los valores esperados.
- Campo obligatorio ausente: rechazar la entrada.
- Plantilla inexistente: rechazar la operación.
- Tipo de bloque incompatible: informar el error.
- Valor con caracteres HTML especiales: comprobar el escape.
- Marcador sin resolver: impedir que la salida se considere válida.

La prueba no debe llamar a la API operativa, modificar JSON de proyectos, ejecutar servicios ni alterar archivos originales.

### 11.7 Criterio de aceptación

El diseño se considerará preparado para implementación cuando se definan el esquema JSON exacto, el registro de plantillas, las reglas de escape, el formato de errores y los resultados esperados de cada caso de prueba.

Esta autorización permite documentar y preparar la prueba aislada. No autoriza modificaciones del código operativo ni la integración en producción.
